     -- Returning 200 OK with an error message breaks API consumers because a 200 status tells the client that the request was successful. Most frontend applications first check the HTTP status code. task 5.1
     -- Lines starting with `>` are the HTTP request headers sent by curl to the server, such as GET, Host, User-Agent, and Accept.
     -- Lines starting with `<` are the HTTP response headers returned by the server, such as HTTP/1.1 200 OK, Content-Type, Content-Length, and Date.
     -- The blank line separates the HTTP headers from the response body. Everything above the blank line is metadata (headers), and everything below it is the actual JSON data.
     -- The `Host` header is automatically sent by curl with the value `jsonplaceholder.typicode.com`. It tells the server which website or virtual host the request is intended for.

task 5.2
     -- The POST request returns the newly created resource with an assigned id (typically 101 in JSONPlaceholder). The GET request uses that id to retrieve the resource.
     -- In a real application, the Service Layer should make the POST request. The UI component should only collect user input and display the results. The Service Layer contains the business logic, validates the data, communicates with the API, and then passes the response back to the UI.
     -- The Repository Layer is responsible for interacting with the data source (such as a database or an external API) and should not contain business logic. The Service Layer calls the Repository Layer to perform data operations, keeping the application modular, reusable, and easier to maintain.

task 6.2
     -- List all projects: GET | /projects | 200 OK

     -- Get a specific project: GET | /projects/{projectId} | 200 OK

     -- Create a project: POST | /projects | 201 Created

     -- List all projects an intern is assigned to: GET | /interns/{internId}/projects | 200 OK

     -- Assign an intern to a project: POST | /projects/{projectId}/interns/{internId} | 201 Created

     -- Remove an intern from a project: DELETE | /projects/{projectId}/interns/{internId} | 204 No Content

     -- Both `POST /projects/{id}/interns/{internId}` and `POST /interns/{id}/projects/{projectId}` are valid REST designs. The choice depends on which resource is considered the owner of the relationship.

     -- If the application is project-centric (managing team members within projects), then `POST /projects/{projectId}/interns/{internId}` is more appropriate because the project owns the assignment.

     -- If the application is intern-centric (managing an intern's profile and assignments), then `POST /interns/{internId}/projects/{projectId}` is a better choice because the intern owns the relationship.

     -- The owner resource is determined by the primary focus of the application and which resource naturally manages the relationship.
